# 라이브 검증 요청 목록 (2026-09-18)

공식 매뉴얼(Zendesk) 오류 제보 과정에서 **문서만으로는 결판이 나지 않는 항목**을 모았습니다.
실제 API 응답으로 확인해 주시면 제보의 방향과 우선순위가 확정됩니다.

## 왜 필요한가

이 저장소(`MIDAS-API`)는 공식 문서를 옮겨 적은 문서 저장소라, 공식 문서가 틀렸는지 판단할 때
쓸 수 있는 근거가 **공식 페이지 내부 증거뿐**입니다. 표와 예제가 서로 다른 값을 제시하거나
한글/영문 로케일이 갈리면 어느 쪽이 정본인지 문서 안에서는 결론이 안 납니다.

실제로 2026-09-06에 `/ope/MEMB` 건을 한글 페이지만 보고 판단했다가 **방향이 반대인 오류 제보를
올렸다가 철회한 사고**가 있었습니다(Jira `MAPI-2484` A-7). 반대로 `MAPI-2375`는 담당 개발자가
실동작을 확인해 "표에 적힌 `SET_STORY_DRIFT_METHOD`는 유효하지 않은 필드라 입력해도 조용히
무시된다"는 결론으로 종결됐습니다. 라이브 결과는 문서 논쟁의 심판 역할을 합니다.

## 검증 방법 (공통)

1. **베이스 페이로드는 공식 아티클의 예제를 그대로** 쓰고, **한 번에 한 필드만** 바꿉니다.
2. **HTTP 200만으로 판정하지 마십시오.** 가장 중요한 부분입니다. MIDAS API는 모르는 필드를
   거부하지 않고 **조용히 무시**하는 경우가 있습니다(`MAPI-2375` 선례). 반드시 POST 직후
   **GET으로 다시 읽어 값이 실제로 반영됐는지** 확인해 주세요.
3. 따라서 각 항목의 판정은 세 갈래입니다: **거부(에러)** / **수용·반영됨** / **수용되나 무시됨**.

## A. 결판형 — 결과에 따라 제보 방향이 바뀜

### A-1. `/ope/MEMB` — 요청 필드명이 `SELETION_TYPE`인가 `SELECTION_TYPE`인가

- 아티클 `49514964272665` ([영문](https://support.midasuser.com/hc/en-us/articles/49514964272665))
- **모순:** Specifications 표 2행 Key는 `"SELETION_TYPE"`(한/영 각 1회)인데, 같은 페이지의
  Input JSON 예제는 한/영 모두 `"SELECTION_TYPE"`입니다.

**절차** — 반드시 `ASSIGN_TYPE: "MANUAL"` + 선택 지정 조합으로 하십시오.
`"AUTO"`/`"ALL"` 조합은 이 필드가 무시돼도 결과가 같아 보여서 판별력이 없습니다.

```jsonc
// (a) 기준: 공식 영문 예제 그대로
{ "Argument": { "ASSIGN_TYPE": "MANUAL", "SELECTION_TYPE": "SELECTION",
                "ELEM_LIST": [640, 692], "ALLOW_SINGLE": false } }

// (b) 키 이름만 표 표기로 교체
{ "Argument": { "ASSIGN_TYPE": "MANUAL", "SELETION_TYPE": "SELECTION",
                "ELEM_LIST": [640, 692], "ALLOW_SINGLE": false } }
```

**해석**

| (b) 결과 | 결론 |
| --- | --- |
| 거부(에러) | 표가 오타. 표를 `SELECTION_TYPE`으로 정정 요청 — 현재 제보 내용이 맞음 |
| 수용 + 선택 반영됨 | 두 키가 별칭. 표는 오타지만 무해 → 우선순위 낮춤 |
| 수용되나 선택 미반영 | **조용히 무시.** `MAPI-2375`와 같은 유형이라 가장 위험 — 우선순위 올림 |

### A-2. `/db/SSEIS` — `SEIS_CODE` 값의 콜론 뒤 공백

- 아티클 `58908676674585`
- **모순:** 한글 페이지의 **복사용 예제**는 `"SEIS_CODE": "KDS(41-17-00: 2019)"`(공백 있음)인데,
  영문 예제와 JSON Schema의 `const`는 `"KDS(41-17-00:2019)"`(공백 없음)입니다. 같은 한글
  페이지의 Specifications 표도 공백이 없어 페이지 안에서 어긋납니다.
- `SEIS_CODE`는 스키마상 `const`라, 표기가 다르면 검증에 걸릴 수 있습니다.

**절차:** 동일 페이로드로 두 철자를 각각 전송.

```jsonc
"SEIS_CODE": "KDS(41-17-00:2019)"    // (a) 공백 없음
"SEIS_CODE": "KDS(41-17-00: 2019)"   // (b) 공백 있음 — 한글 예제를 그대로 복사한 형태
```

**해석**

| (b) 결과 | 결론 |
| --- | --- |
| 거부 | **한글 예제를 복사하면 실패한다**는 실사용 피해가 확정 → A-8 최우선 근거 |
| 수용 | 서버가 공백을 정규화하는 것. 표기 통일 요청 수준으로 낮아짐 |

### A-3. `/db/TDNA` — `RADIUS`의 타입

- 아티클 `35954555962137`
- **모순:** Specifications 표에서 같은 `"RADIUS"` 항목이 구간별로 세 가지 타입입니다.

| 구간 | 표 표기 | JSON Schema |
| --- | --- | --- |
| `PROFY` (2D Round, x-y) | `Boolean` / 기본값 `false` | `"type": "number"` |
| `PROFZ` (2D Round, x-z) | `Number` / `0` | `"type": "number"` |
| `PROF` (3D Spline) | `Array` / `0` | `"type": "number"` |

스키마는 세 분기 모두 `number`이고, 3D 예제도 `"RADIUS": 0` · `"RADIUS": 20` 스칼라입니다.

**절차:** (a) 세 분기 모두 숫자(공식 예제 그대로) → 기준. (b) `PROFY.RADIUS`에 `false`.
(c) `PROF.RADIUS`에 배열 `[0, 20]`.

**해석:** (b)·(c)가 거부되면 표 두 행이 오류로 확정되고, "세 행 모두 `Number`" 요청이 확정됩니다.
혹시 (c)가 **수용**된다면 3D 분기만 실제로 배열을 받는다는 뜻이므로, 그때는 스키마 쪽이 틀린
것이라 제보 방향이 반대가 됩니다. **이 가능성 때문에 확인이 필요합니다.**

## B. 보강형 — 결론은 문서로 났고, 라이브가 근거를 강화

### B-1. `/db/SSEIS` — 오타 키 `IINHERENT_TORSION` / `NHERENT_TORSION`

정상 키는 `INHERENT_TORSION`입니다. 공식 예제에 오타 형태가 남아 있어, 그대로 복사해 보내면
어떻게 되는지 확인해 주세요. **무시된다면** "예제를 복사하면 해당 옵션이 조용히 빠진다"는
구체적 피해가 되어 제보의 무게가 달라집니다.

### B-2. 표에서 누락된 필드가 실제로 동작하는지

아래 필드들은 **JSON Schema·예제에는 있는데 Specifications 표에 행이 없습니다.** GET 응답에
나오는지, POST/PUT으로 설정했을 때 반영되는지 확인해 주시면 "표 누락" 제보가 확정됩니다.

| --- | --- |
| `/db/MATD` | `bSERVCHECK` · `dSHORTTERM` · `dLONGTERM` |
| `/db/SPLC` | `ALONG` |
